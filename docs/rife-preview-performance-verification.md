# RIFE生成後の編集画面の負荷と耳の枠（2026-09-17）

## 原因と修正

口の確認画面は、更新ごとに8枚×96三角形のSVGと操作要素を再構築していた。検証データでは口だけで23,652要素があり、スライダー・ズーム・ドラッグでメインスレッドを長時間占有した。前回の口単体Canvasベンチマークは、このDOM再構築の負荷を含めていなかった。

RIFEの口の確認には、口領域だけの512px描画キャッシュを使用する。スライダーと拡大・移動ではキャッシュを再利用。素材・再生設定・生成結果が変わると更新し、確認を閉じると解放する。遅れて終了した準備処理も破棄する。元のSVGと中間コマは保持し、直接編集に入るとSVGの編集ハンドルへ戻る。API/MCPの生成・状態取得・保存処理は共通のまま。

耳の枠は、VTracer由来の透過マスクで、白いキャンバスを黒い「キャンバスから耳を除いた形」で覆う構造のアンチエイリアスが原因。縮小や端数座標で、白と黒の四角い端が完全には相殺されない。既知のalphaマスクの完全な白四角＋黒い外周の組み合わせだけを、内側の既存の耳形状へ置き換えて描画する。通常のアートや編集済みの別構造のマスクは変更しない。素材の保存データは変更せず、プレビュー・シーンSVG出力に適用する。

## 検証

既存の20パーツの同一検証プロジェクトを、修正前配布版と修正後で比較。ユーザーが作業している18765のアプリ・未保存プロジェクトには変更を加えず、専用データ・18788ポート・headless Edgeを使用。

- 修正前: 口の更新処理1,689.6〜2,983.3ms、入力から2描画フレーム待つまで2,221〜3,589ms。
- 修正後: 口の更新処理1.5〜2.0ms、同じ2フレーム待ち22〜34ms。口のSVG表示要素はクリック用の1要素。
- 12回のスライダー操作とズームでキャッシュ生成は1回。ON/OFFや再生成時には作り直す。
- 生成直後の更新1.7ms。スクロール、再生成、口をクリックして直接編集に戻りハンドルが現れることを確認。
- 配布用バックエンドでも同じ操作を再確認。更新1.6〜7.0ms、生成直後2.8ms。耳の外側alphaも同じ結果で、ブラウザ例外なし。
- 元PNG・修正前SVG・修正後SVGを、実プレビューと同じ1024/1280倍・端数座標で比較。耳の外側45画素のalpha合計は元PNG=0、修正前SVG=1445、修正後SVG=0。元PNGに枠はなく、SVGマスクの表示で生じることを再現した。
- JavaScript全体253件成功。その後追加した口領域キャッシュ用のテストを含む対象17件も成功。

値はこの検証データ・環境での測定で、キャラクター全体のFPSを示すものではない。元PSDそのものは再編集せず、保存済みプロジェクトに含まれるPSD由来の元PNGを比較に使用した。
